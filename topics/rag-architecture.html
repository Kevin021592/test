檢索增強生成（Retrieval-Augmented Generation, RAG）

分類：生成式 AI 與語言模型 整理日期：2026-11-22 資料出處：iPAS-AI 應用規劃師能力筆記

核心定義

RAG 就是先把相關知識找給 LLM，讓 LLM 去理解與生成，是 LLM 的「外掛」，不是必須 LLM 一定要有的東西。
注意：RAG 只能降低幻覺，無法完全解決幻覺；RAG 本身不理解問題，LLM 才是真正理解與推理者。

重點速覽

  • R (Retrieval, 檢索)：把問題向量與向量資料庫內的向量比對相似度，找出最相關的資料 chunk 或文件，傳回流程層。檢索階段不做推理，只做「語意距離計算」。
  • A (Augmentation, 增強)：將「檢索到的外部相關內容」整理、把資料變成 prompt，讓 LLM 在「有依據」的情況下回答。
  • G (Generation, 生成)：LLM 取得素材後，去做理解問題跟回應問題的工作，所以 RAG 的 G 一定會用到生成式語言模型。
  • 導入順序策略：先選一個現成模型（GPT、Claude、LLaMA） → 用 Prompt / Workflow 解問題 → 不夠再考慮 RAG → 最後才想 Fine-tuning。
  • 與 ChatGPT / Gemini 的關係：常用工具在某些功能與模式下會使用 RAG，但 LLM 本體本身不等於一定有 RAG。

詳細解析

一、RAG 完整運作 9 大流程步驟

流程中第 2～5 步屬於 R（檢索）、第 6 步屬於 A（增強）、第 7 步屬於 G（生成）：

  1. 使用者輸入問題：使用者在介面（App、網頁、聊天視窗）打字，例如：「請問今天的天氣看起來會有需要帶傘嗎？」
  2. 問題轉換為向量（Query Embedding）：系統把這句問題送進 embedding 模型，轉成一組數字向量。這一步用的模型必須跟當初把文件切成 chunk 時用的同一個 embedding 模型，兩者的向量才有可比性。
  3. 拿問題向量去向量資料庫比對：系統拿這個向量去 Chroma（或 Milvus、Weaviate 等）裡，跟資料庫裡所有 chunk 的向量做相似度計算（通常是餘弦相似度），找出最相似的 Top-N 筆（比如 Top 3）。
  4. 取回 Top-N 個 chunk 及其 metadata：資料庫回傳這幾筆最相關的 chunk 原文，連同各自的 heading_path、source_file 等 metadata。
  5. （可選）依 metadata 做額外篩選或排序：如果使用者有指定條件（比如只查「天氣」相關），系統可以在這一步用 metadata 做精準篩選，或用其他規則重新排序（例如優先給較新的文件）。
  6. 組裝 Prompt：程式把「固定的系統指示」+「第 4 步取回的 chunk 內容」+「使用者原本的問題」，組成一段完整文字，準備送給 LLM。這一段完全是程式自動組裝，使用者看不到。
  7. 送給 LLM 生成答案：把組好的 prompt 送到 LLM API（Claude、GPT 等）。LLM 讀過這些 chunk 內容後，用自己的話統整、歸納，生成一段通順、針對使用者問題的回答。
  8. （可選）加上引用來源：有些系統會要求 LLM 在回答時附上「這段資訊來自哪個檔案、哪個章節」，這時候第 4 步取回的 source_file、heading_path metadata 就會被用上，讓答案可以標註出處，方便使用者查證。
  9. 答案回傳給使用者：最終生成的文字答案顯示在介面上，使用者只看到這個結果，中間第 2～8 步全部是系統內部運作，對使用者是隱形的。

二、細節技術：建立向量資料庫的過程

1. 切片（Chunking）

作用：把原始知識文件切成「剛好能被搜尋、又剛好能被 LLM 理解」的小段文字，Chunking 的設計本質是在定義「最小可回答單位」。

  • 切得好 → RAG 準
  • 切得爛 → 找不到 / 找到碎片，但看不懂上下文 / LLM 亂講

Chunk 通常怎麼切？

  • 依字數 / token 切（最常見）：約 300–500 tokens 一個 chunk，每個 chunk 之間 overlap 50–100 tokens。
  • 依結構切（更好，適合文件有明確結構）：標題、段落、條款、FAQ。
  • 依語意切（進階，實作複雜且成本高）：用 NLP / LLM 判斷「主題轉換點」，每個 chunk 是一個「完整語意單元」。
特性 切得小 (Small Chunk) 切得大 (Large Chunk)
語義精確度 高。能精準定位到某個具體的事實或數據。 低。檢索出來的內容可能包含太多雜訊。
上下文完整性 差。容易出現「斷章取義」，AI 搞不清楚主詞是誰。 好。保留了完整的脈絡、因果關係與背景。
檢索效率 快。向量比對較輕量。 慢。處理長向量或長文本塊較吃資源。
Token 成本 低。餵給 LLM 的廢話較少。 高。餵給 LLM 很多無關的廢話，浪費錢。
典型數值 約 128 - 256 Tokens 約 512 - 1024 Tokens 以上

2. 語意向量化（Embedding）

作用：將文字、句子、甚至整個文件（這些是電腦無法直接處理的非結構化資料）轉換成數值向量，保留語意資訊。會發生在「使用者輸入問題的時候」與「建立向量資料庫的時候」。

資料類型 用什麼 Embedding
文件 / 文字 文字 embedding（語意向量）
PDF / 表格 文字 embedding（先抽文字再轉向量）
圖片 圖片 embedding（CNN、CLIP 等模型）
音頻 / 語音 音頻 embedding（聲音特徵向量）
行為序列 / 時序資料 行為 embedding（時間序列向量）

3. 向量資料庫建立（Vector Database）

作用：將語意向量儲存在資料庫中，使用「相似度比對」找到最相關的結果。

  1. 原始知識文件（PDF、文章、報告、客服 FAQ 等）先被切成小段落或片段（chunk）。
  2. 每個 chunk 生成 embedding。
  3. 存到向量資料庫。
  4. 建立向量索引：把知識庫的每個 chunk / 文件 embedding 存成索引，支持快速相似度搜尋（近似最近鄰 / ANN）。

*註：這個過程當中，向量資料庫建立是可以一直被動態調整的，也就是說它可以隨時新增資料（文件、檔案...），只要今天要新增一份檔案，也是一樣會經過：切片 chunk → 生成 embedding → 建立向量資料庫 → 建立向量索引。

三、RAG 的優點與缺點

優點：

  • 避免讓 LLM 胡說八道：降低幻覺產生。
  • 保護資料：資料不需要被上傳到雲端，只是在回答問題的那一瞬間，把相關的片段「借」給模型閱讀，閱讀完就結束，不會借走知識。
  • 即時更新：今天給它新資料，它馬上就可以回答新答案了。
  • 附上出處，方便查證：可以附上參考資料的來源。

缺點：

  • 速度變慢：因為要查的東西變多了。
  • 建置複雜度（Complexity）：單用 LLM 只要呼叫一個 API；做 RAG 需要維護一個「向量資料庫 (Vector Database)」，還要寫程式去把文件切碎（Chunking）、轉檔、索引。

四、RAG 的過程，哪裡會需要人的設計？

  • Chunking 規則：非常吃經驗，像是：一個 chunk 要多大、怎麼切。
  • 檢索結果的「篩選與排序策略」：搜尋向量資料庫後，要選 top 幾個結果出來？有沒有要加入條件，像是「不能混不同文件類型」、「一定要是當年度資料」等。
  • Prompt 組裝：規定資料要怎麼放進 prompt、哪些資料優先、LLM 可以/不可以做什麼（例如：「只能根據以下提供的資料回答，如果資料不足，請回答資料不足，請勿自行推測」）。
  • 人工審核 / 回饋（Feedback Loop）：使用者點選「有幫助 / 沒幫助」，據以調整 chunking、調整搜尋前幾名結果或調整 prompt。

五、評估指標：RAGAS（衡量檢索內容與回答的相關性）

三大核心指標：

  • Faithfulness (有沒有亂掰)：回答內容是否忠實於檢索到的知識片段。
  • Answer Relevance (有沒有回答到問題)：生成結果是否精準針對提問。
  • Context Relevance (檢索有沒有找對東西)：檢索出的內容是否真正與問題相關。

價值：利用模型本身去衡量回答與檢索內容之間的關係，把原本主觀的人工判斷轉成可持續監控的量化指標。

六、RAG 與 微調 (Fine-tuning) 的比較

特性 RAG（帶書考試） Fine-tuning（入腦特訓）
知識更新 只要更新資料庫就好，非常快。 每次都要重新訓練，又慢又貴。
防止幻覺 效果好，因為有原文對照。 效果普通，AI 仍可能亂編。
語氣 / 格式掌控 普通（靠 Prompt 引導）。 極佳（直接改變模型行為）。
私密資料安全性 資料放在自己的資料庫。 資料必須餵給模型訓練。
溯源能力 有（可標註出處）。 無（知識已混合在一起）。

參考資料與真題補充

  • 來源文件：iPAS-AI 應用規劃師能力筆記（第 8～12 頁）
  • 114-4 第二科 Q17 RAG 與 Fine-tuning 結合維護策略：當系統需同時確保回覆語氣一致、能即時查詢每日新增文件、維持效能穩定時，最合適策略為「保留語氣相關 Fine-tuning，僅透過檢索系統更新文件內容，不頻繁改動模型」。

  • 114-4 第二科 Q44 RAG 與 MCP 核心差異：RAG 常用於擴展知識庫內容，而 MCP 更著重於動態工具與 API 呼叫的整合。
